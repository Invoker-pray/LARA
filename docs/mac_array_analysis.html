16×16 计算过程：

  1. Q[0:15][:] 和 K[0:15][:] 加载到阵列边界
  2. 128 个 head_dim 元素逐个流入（depth iteration），每个元素触发 16×16=256 次 MAC
  3. 每个 PE 内部累加 128 个部分积 → 输出 S[i,j]
  4. Softmax Engine 处理 16 行 × 16 列 = 256 个 S 值，分 4 次 (每次 16 列)
  5. 状态：m[0..15] 16 个 max 寄存器, l[0..15] 16 个 sum 寄存器

16×32 的优势：

  1. 行数不变 (16) → Softmax 引擎不变 — 不需要增加 m/l/acc 寄存器
  2. 列数翻倍 (32) → 每个子块覆盖 2× 的 K 列 → 子块数减半
  3. fanout 不变 (每行 Q 广播给 32 个 PE vs 16 个 PE) — 但这是列方向的，走的是列广播线，不是行方向
  4. 列归约树深度 +1 (log₂32=5 vs log₂16=4) — 时序影响可控

3. 为什么 16×32 比 32×32 好 — 核心原因

原因一：Softmax 引擎的并行度瓶颈

这是最关键的约束。Online Softmax 需要为每行 Q 维护独立的状态：

// Online Softmax 每行 Q 的状态
for i in 0..NUM_ROWS-1:                    // ← 这个数字决定了硬件并行度
    m_new[i] = max(m[i], row_max(S[i,:]))     // 需要: 1 个比较器树 / 行
    correction[i] = exp(m[i] - m_new[i])       // 需要: 1 个 EXP LUT + 1 个减法器
    P_row[i] = exp(S[i,:] - m_new[i])          // 需要: 1 个 EXP LUT + 1 个减法器 / 元素
    l[i] = l[i] × correction[i] + sum(P_row)   // 需要: 1 个加法器树 + 1 个乘法器 + 1 个加法器
    O_acc[i,:] = O_acc[i,:] × correction[i] + P_row[i] × V_tile
硬件16 行 (16×16 / 16×32)32 行 (32×32)
max 归约树 (每行) 16 棵树, log₂(Tk) 深度 32 棵树 → 2× LUT/FF
sum 归约树 (每行) 16 棵树 32 棵树 → 2× LUT/FF
EXP LUT (每行) 16 个 BRAM 端口或分时复用 32 个 → 1 个 BRAM 不够, 需要 2 个
m/l/O_acc 状态寄存器 16 组 × (1+1+128) fp32 ≈ 8 KB 32 组 ≈ 16 KB
O_acc 修正乘法 + 加法 16 路并行 32 路 → 2× DSP
关键洞察：MAC 阵列可以做大，但 Softmax 引擎的并行度必须和 MAC 阵列的行数匹配。
16 行 → Softmax 处理 16 行并行 → 硬件开销合理
32 行 → Softmax 处理 32 行并行 → 硬件翻倍，成为新的瓶颈
MAC 阵列的行数由 Softmax 引擎的合理并行度决定，而非 DSP 数量。

原因二：Q 数据加载与广播

16 行阵列:
  Q 加载: 16 × 128 × 2B = 4 KB / 子块
  广播: 每行 Q 值广播到 C 个 PE → fanout = C

32 行阵列:
  Q 加载: 32 × 128 × 2B = 8 KB / 子块
  广播: 每行 Q 值广播到 C 个 PE → fanout 不变
  但 32 行需要 32 条独立的广播线 → 布线密度 2×

对 32×32: 32 条行广播线, 32 条列广播线 → 64 条总广播线
对 16×32: 16 条行广播线, 32 条列广播线 → 48 条总广播线
→ 16×32 的布线压力小 25%

原因三：时序收敛

关键路径分析 (200MHz = 5ns 周期):

16×16:
  PE 内部 bf16 MAC: ~2.5ns (DSP48E2 乘法 + 累加)
  行广播 fanout=16: ~0.5ns
  列归约 fanout=16 (4级): ~1.0ns
  余量: ~1.0ns ✓

16×32:
  PE 内部 bf16 MAC: ~2.5ns (不变)
  行广播 fanout=16: ~0.5ns (不变!)
  列归约 fanout=32 (5级): ~1.3ns → +0.3ns
  余量: ~0.7ns → 可接受, 可能需要 pipelining

32×32:
  PE 内部 bf16 MAC: ~2.5ns
  行广播 fanout=32: ~0.8ns → +0.3ns
  列归约 fanout=32 (5级): ~1.3ns → +0.3ns
  额外: 1024 PE 的布线拥塞 → ~0.3ns
  总: ~4.9ns → 余量仅 0.1ns → 高风险 ✗

原因四：赛题约束 & 论文叙事

16×16 → 256 DSP (20%) → "克制"
16×32 → 512 DSP (41%) → "适度扩展"
32×32 → 1024 DSP (82%) → "堆资源"

从 16×16 到 16×32: 论文可以写 "2× 列并行度, 子块数减半, 时序可控"
从 16×16 到 32×32: 论文写 "4× 阵列, 但 Softmax 硬件也翻倍" → 说明效率不高

🎯 核心结论

MAC 阵列的行数受限于 Softmax 引擎的并行度，而非 DSP 数量。

Online Softmax 需要为 每行 Q 维护独立的 (m, l, O_acc) 状态，并进行 max/sum/exp/div 运算。
阵列行数翻倍 → Softmax 硬件翻倍 → 这个代价远大于多加几个 DSP。

16 行是 Softmax 硬件复杂度的 sweet spot：16 路 max 树 + 16 路 sum 树 + 1 个双端口 BRAM EXP LUT 刚好够。
32 路则需要 2 套独立的 Softmax 硬件，或者 1 套分时复用（增加延迟和状态机复杂度）。

因此：

  • 扩展列数 (16→32)：只增加 MAC PE 和列归约深度，Softmax 不变 → 安全扩展
  • 扩展行数 (16→32)：要求 Softmax 硬件翻倍 → 瓶颈转移，得不偿失

这个约束同样解释了为什么 CIM 毕设选择 16 行而不是 32 行 — 16 行的部分和累加器 (psum_accum) 复杂度恰好是拿 LUT/FF 可以高效实现的临界点。
