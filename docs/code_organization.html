Pipeline Order (one GQA group, one Q_tile):
① CSR_LOAD_REQ 驱动当前 group 的 K/V DMA → ② Q_tile 请求加载 (DDR→Ping-Pong) → ③ Q×K^T (MAC Phase A) → ④ Scale + Mask → ⑤ Online Softmax → ⑥ P×V (MAC Phase B) → ⑦ O Accumulate → ⑧ Normalize + bf16 Truncate → ⑨ O_tile Writeback (DDR)
Key Design Decision — Host-Side QKV Projection: QKV 投影由 host_attention.py 在 ARM/宿主机完成，再由 driver 转换为 head-major bf16 并通过 DMA 送入 PL。 投影权重不进入当前 bitstream，避免与 Attention MAC 阵列争用资源。 端到端性能必须分别报告 host projection、DMA 和 PL compute 时间，不能继续使用早期固定频率估算代替实测。

3. Data Type Specifications

3.1 bf16 (Brain Floating Point 16)

FieldBitsEncoding
Sign[15]0=positive, 1=negative
Exponent[14:7]8-bit, bias=127. Range: 2-127 to 2128
Mantissa[6:0]7-bit fractional. Implicit leading 1 → effective 8-bit precision
S E7E6E5E4E3E2E1E0 M6M5M4M3M2M1M0
Value = (-1)^S × 2^(E-127) × 1.M
Dynamic range ≈ fp32 (±3.4×1038), precision ≈ 3 significant decimal digits
Key property: bf16 → fp32 conversion is trivial — pad mantissa with 16 zeros. No rounding needed.
Storage: 2 bytes per element. Alignment: 16-bit boundary in memory.
Special values: E=0xFF, M≠0 → NaN; E=0xFF, M=0 → ±∞; E=0, M=0 → ±0; E=0, M≠0 → subnormal

3.2 fp32 (IEEE 754 Single Precision)

Format: 1-bit sign + 8-bit exponent (bias=127) + 23-bit mantissa (implicit leading 1)
Used for: All intermediate accumulation results. The 23-bit mantissa provides enough precision for accumulating up to 2^(23-7) = 65536 bf16 products without rounding error.
Storage: 4 bytes per element. Alignment: 32-bit boundary.

3.3 Internal Data Representations

StageFormatWidthRationale
Q/K/V input (DDR) bf16 16-bit Matches Llama3.1-8B checkpoint format
MAC multiply operands bf16 16-bit DSP48E2 accepts 16-bit operands
MAC product (per PE) fp32 32-bit bf16×bf16 → exact fp32 product (DSP48 27×18 multiplier)
Partial sums (column reduction) fp32 32-bit Column accumulation of up to 16 products — fp32 mantissa sufficient
S_tile (Q×K^T result) fp32 32-bit Streamed directly to Softmax; never stored in SRAM
P_tile (after Softmax) fp32 32-bit Streamed directly to MAC Phase B; never stored in SRAM
O_acc (accumulated output) fp32 32-bit Accumulated across all KV tiles; must maintain precision
O_final (DDR writeback) bf16 16-bit Truncated from fp32 only at final step; matches original precision
m (running max per row) fp32 32-bit Online Softmax state; must match S_tile precision
l (running sum per row) fp32 32-bit Accumulates exp() values; 当前验证范围为 L≤512，更长序列需要分页策略

Input Data Structure (a_bf16 / b_bf16):
Two bf16 operands. In Phase A (Q×K^T): a = one Q element, b = one K element.
In Phase B (A×V): a = one P (attention weight) element cast from fp32 to bf16, b = one V element.

Input Data Structure (c_fp32):
fp32 partial sum. In a systolic column: output of the PE above (or 0 for the first PE).
For a row of 128 head_dim elements: PE accumulates 128 products, one per cycle.

Output Data Structure (out_fp32):
fp32 result = Σ(a_i × b_i) + c_initial. This is one element of the S_tile (Phase A) or one partial output contribution (Phase B). Feeds into column reduction tree.
DSP48E2 Mapping: The 9-bit mantissa multiplication (1.m × 1.m, where m is 7-bit) maps directly to DSP48E2's 27×18 multiplier. The exponent addition (8-bit) and sign XOR are done in FPGA logic (LUTs). The fp32 accumulation uses the DSP's 48-bit accumulator or a separate fp32 adder. Round-to-nearest-even must match Python's ml_dtypes.bfloat16 behavior exactly for bit-accurate verification.

attn_tile.sv — Time-Multiplexed Compute Array

Pipeline Position: Central Compute Engine ← Q from tile_buffer, K/V from kv_cache_ram → S_tile/P_tile to softmax_engine/psum_accum ↻ Phase A (Q×K^T) and Phase B (P×V) time-multiplexed

Phase A: Q×K^T Computation

Task: Q_tile [Tq, 128] × K_tile^T [128, Tk] = S_tile [Tq, Tk]

With TILE_ROWS=16, TILE_COLS=16, Tq=32, Tk=64, head_dim=128:

Outer loop: S [32,64] decomposed into (32/16)×(64/16) = 2×4 = 8 sub-blocks
Each sub-block: [16,16] computed by the array in one pass.

Inner (depth) loop: 128 / TILE_SPLIT_FACTOR iterations.
  - Each cycle: 16 Q elements broadcast to 16 rows, 16 K elements broadcast to 16 cols
  - 16×16 = 256 parallel bf16 multiplications
  - Column reduction: each column sums 16 PE outputs → 16 fp32 values

Data flow per cycle (TILE_SPLIT_FACTOR=16, 1 element processed/cycle):
  Q[0..15][depth]  ──row broadcast──→ PE[row, 0..15]  ←──col broadcast── K[0..15][depth]
                                              │
                                     256 parallel bf16 MACs
                                              │
                                   Column reduction (16×)
                                   Each column: Σ(row=0..15) PE[row,col]
                                              │
                                   col_out[0..15] = S_block[row_start..row_start+15, col_start..col_start+15]
                                              │
                                   Streamed directly to softmax_engine (NOT stored in SRAM)

Phase B: P×V Computation

Task: P_tile [Tq, Tk] × V_tile [Tk, 128] = ΔO [Tq, 128]

Same array, different operands:
  Row input: P[i][k] (fp32, cast to bf16 for multiplication)
  Col input: V[k][j] (bf16)
  Output: ΔO[i][j] contribution for this KV tile

Since Tk (64) > TILE_COLS (16):
  For each row i ∈ [0..Tq-1] and each V column block j ∈ [0..(128/16)-1]:
    Accumulate Σ(k=0..Tk-1) P[i][k] × V[k][j_block*16 .. j_block*16+15]

The column outputs are partial ΔO contributions.
psum_accum collects and accumulates these across V column blocks and KV tiles.
Key Data Structure — S_tile (Phase A output):
Shape: [TILE_ROWS × TILE_COLS] = [16 × 16] fp32 values.
Each element S[i,j] = Σ(depth=0..127) Q[row_start+i][depth] × K[col_start+j][depth].
These are streamed directly to softmax_engine — NOT written to SRAM.
This is the FlashAttention optimization: the full [Tq,Tk] S matrix materializes only as a series of small [16,16] blocks flowing through the pipeline.

Key Data Structure — col_out (column reduction):
16 × fp32 values per cycle. Each value = Σ(row=0..15) PE[row][col].
Feeds into psum_accum for further reduction and the softmax_engine for exp/max/sum operations.
Time Multiplexing Rationale: Using one 16×16 array for both Q×K^T and P×V saves a second physical MAC array. The current split/reuse implementation routes with 165 DSPs. The array is idle during Softmax computation, which takes ~O(Tk) cycles. For Tk=64, the idle time is acceptable (pipeline bubble). If Softmax latency becomes the bottleneck, double-buffering the MAC array inputs can help.

Online Softmax Algorithm (Hardware Implementation)

// For each row i ∈ [0..TILE_ROWS-1], parallel hardware:
// Process one S_tile sub-block [TILE_ROWS × TILE_COLS]

if (kv_tile_first) begin
    m[i] = -inf;        // fp32 minimum
    l[i] = 0;           // fp32 zero
    O_acc[i][0..127] = 0;
end

// Step 1: Scale S by 1/√128
for each S[i][j]:
    S_scaled[i][j] = S[i][j] * (1/√128)    // fp32 multiply by constant

// Step 2: Find row-wise max (over this sub-block)
for each row i:
    row_max[i] = max(S_scaled[i][0..TILE_COLS-1])  // reduction tree, log2(TILE_COLS) depth

// Step 3: Update running max
m_new[i] = max(m[i], row_max[i])

// Step 4: Compute correction factor
correction[i] = exp(m[i] - m_new[i])       // EXP via LUT (1 cycle)

// Step 5: Compute P (attention weights for this sub-block)
for each S_scaled[i][j]:
    P[i][j] = exp(S_scaled[i][j] - m_new[i])   // EXP via LUT (1 cycle)

// Step 6: Update running sum
row_exp_sum[i] = sum(P[i][0..TILE_COLS-1])     // reduction tree
l[i] = l[i] * correction[i] + row_exp_sum[i]

// Step 7: Update running output accumulator
// Handled by psum_accum + output_buffer:
O_acc[i][:] = O_acc[i][:] * correction[i] + Σ(j) P[i][j] * V[j][:]

// Step 8: Final normalization (only after last KV tile)
if (kv_tile_last) begin
    O[i][:] = bf16( O_acc[i][:] / l[i] )     // fp32 divide + bf16 truncate
end
Critical Data Structures:

m_state [16 × fp32]: Running maximum per Q row. Initialized to -inf at each Q tile start. Updated every KV tile. The correction factor exp(m_old - m_new) is always ≤ 1, ensuring numerical stability. After 8 KV tiles (Tk=64, TILE_COLS=16), m converges to the global row max.

l_state [16 × fp32]: Running sum of exp(S - m). Each KV tile contributes row_exp_sum to l, after the old l is corrected by exp(m_old - m_new). At the end: l[i] = Σ(j=0..Tk-1) exp(S[i][j] - m_final[i]) — the softmax denominator.

O_acc [16 × 128 × fp32]: Running weighted sum of V. Each KV tile adds P_block × V_block after correcting the old O_acc by exp(m_old - m_new). At the end: O_acc[i][:] = Σ(j) P[i][j] × V[j][:] — the unnormalized attention output.

P_tile [16 × 16 × fp32]: The softmax output for this sub-block.

EXP Function Implementation

Method: LUT + Linear Interpolation (current bf16 baseline)

ROM: 1024 entries × fp32 = 4 KB (1 BRAM)
Input range: [-8, 8] (covers exp(-8)≈0.0003 to exp(8)≈2981)
  - Values < -8: clamp to 0
  - Values > 8:  clamp to exp(8) ≈ 2981

LUT addressing:
  addr = (x + 8) * 64    // 1024 entries over 16-unit range → 64 entries per unit
  exp(x) ≈ LUT[addr] + (x - x_base) * (LUT[addr+1] - LUT[addr]) / step

Precision: < 0.1% relative error within [-8, 8]
Latency: 2 cycles (LUT read + interpolation multiply-add)
Resource: 1 BRAM (18Kb, dual-port → 2 reads/cycle for 2 rows)
Parallelism Constraint: The Softmax engine must process TILE_ROWS=16 rows in parallel. This requires: 16 max-reduction trees, 16 sum-reduction trees, 16 EXP LUT ports (or time-multiplexed). This hardware cost is WHY the MAC array row count is capped at 16 — doubling to 32 would double the Softmax hardware, becoming the new bottleneck instead of DSP count.

Computation

// For each row i and each head_dim d:
// O_acc_new[i][d] = O_acc_old[i][d] × correction[i] + Σ(j=0..TILE_COLS-1) P[i][j] × V[j][d]

    O_corrected[i][d] = O_acc_in[i][d] × correction[i]    // fp32 multiply

// Step 2: P × V (reuses attn_tile MAC array in Phase B)
P_tile [TILE_ROWS × TILE_COLS] fp32
V_tile [TILE_COLS × HEAD_DIM] bf16
→ ΔO [TILE_ROWS × HEAD_DIM] fp32

// Step 3: Accumulate
O_acc_out[i][d] = O_corrected[i][d] + ΔO[i][d]           // fp32 add
P×V Matrix Shape Analysis:
P_tile: [16, 16] fp32 — each row is a partial softmax output for one Q position.
V_tile: [16, 128] bf16 — 16 V vectors of head_dim=128.
ΔO: [16, 128] fp32 — contribution to the attention output from this KV tile.
Total FLOPs per sub-block: 16 × 128 × 16 = 32,768 MACs.
Across all sub-blocks for one Q tile (L=512, Tq=32, Tk=64): (32/16) × (64/16) × (128/16) = 2 × 4 × 8 = 64 sub-blocks → ~2.1M MACs per Q tile.

CHECK_GROUP --> LOAD_KV: yes (load new K/V from DDR) CHECK_GROUP --> DONE DONE --> IDLE: interrupt host
Loop Nest Counter Management:
The FSM maintains these nested loop counters internally:
q_tile_idx [0..MAX_N_Q_TILES-1] — outer Q tile loop
kv_tile_idx [0..MAX_N_KV_TILES-1] — inner KV tile loop
head_idx [0..3] — Q head within GQA group
group_idx [0..7] — GQA group

For each GQA group: K and V are the same for all 4 Q heads in the group. So K/V are loaded once per group, and the Q-tile loop runs 4 times (once per Q head).
Total iterations (L=512, Tq=32, Tk=64):
8 groups × 4 heads × (512/32) Q tiles × (512/64) KV tiles = 8 × 4 × 16 × 8 = 4096 inner loop iterations.

  = 512 × 128 × 2 bytes = 128 KB for the current KV head

V Cache: same structure, another 128 KB

  → the physical multi-bank layout uses 48 URAM tiles in the v2.2 routed design.

Current strategy:
  L ≤ 512: cache one KV head pair, reuse it for four Q heads, then reload at the next GQA group.
  L > 512: not implemented; future work requires chunked or paged host transfers.

The 512 limit is an implementation contract, not an assumption about the competition input.

Multi-bank organization for parallel access:
  TILE_KV=64 tokens read simultaneously → 64 parallel data paths
  Bank partitioning: interleave by token index
    Bank 0: tokens 0, 8, 16, ...
    Bank 1: tokens 1, 9, 17, ...
    ...
    Bank 7: tokens 7, 15, 23, ...
  8 banks × 8 tokens/bank = 64 tokens read in parallel
K/V Data Structure Details:
K source tensor: Shape [L, 1024] bf16 in host memory; each request selects one [L, 128] KV-head slice.
Each cached K element is a bf16 value representing one dimension of one key vector.
V source tensor: Shape [L, 1024] bf16; the cache stores the corresponding [L, 128] slice.
Access pattern: Sequential writes while servicing CSR_LOAD_REQ (streaming from DDR). Strided reads during Attention loop: for kv_start=0,64,128,..., read tokens [kv_start .. kv_start+63] across all 128 head dimensions. Each token's K/V is read 16 times (once per Q tile, for L=512, Tq=32).
This is why caching is critical: Within one GQA group, each K/V token is reused by four Q heads and multiple Q tiles. The host sends the slice once per group; subsequent KV-tile reads are served from URAM. Full-layer traffic and latency must be measured from DMA/performance counters.

Ping-Pong Operation

Time ──────────────────────────────────────────────────────────────→

Bank A: [LOAD Q_tile_0] [──── IDLE ────] [LOAD Q_tile_2] [── IDLE ──] ...
Bank B: [──── IDLE ────] [LOAD Q_tile_1] [──── IDLE ────] [LOAD Q_tile_3] ...

MAC:    [── IDLE ──] [COMPUTE tile_0] [COMPUTE tile_1] [COMPUTE tile_2] ...

Q_tile size: TILE_Q × head_dim = 32 × 128 × 2B = 8 KB
DMA latency and MAC time are board/build dependent; do not infer a fixed ratio from payload size.
→ Ping-Pong buffer of just 2×8 KB = 16 KB is sufficient
Q Data Stream Characteristics:
Q is read from DDR exactly ONCE per Q_tile (not reused). Each Q_tile is 32 tokens × 128 dimensions × 2 bytes = 8 KB. After computation, the Q_tile data is discarded — no writeback needed.
This is the complement of K/V: K/V are read many times → cache in URAM. Q is read once → stream through with minimal buffering. Together this minimizes total on-chip memory usage.

AXI4-Stream Data Format:

QKV Projection Computational Analysis:
Q = X @ Wq^T: [L, 4096] × [4096, 4096] = L × 4096 × 4096 MACs.
For L=512: 512 × 4096 × 4096 ≈ 8.6 GMACs.
This projection is intentionally outside the PL timing/resource budget and is measured separately on the host.
K = X @ Wk^T: [L,4096] × [4096,1024] = L × 4096 × 1024 ≈ 2.1 GMACs (L=512).
V = X @ Wv^T: same ≈ 2.1 GMACs.
Total QKV projection: ~12.9 GMACs vs Attention: ~34.4M MACs (L=512, per GQA head pair).
Conclusion: QKV projection is ~375× more compute than Attention for L=512. It MUST stay on the host (ARM CPU or software preprocessing). Do not implement in the current PL attention bitstream. Host projection is integrated through AttentionAccelerator.run_layer().

15.2 rope_engine.sv — Rotary Position Embedding ext

Pipeline Position: QKV Projection → Attention (on Q and K) ← Q/K vectors [head_dim] bf16 + position index → Rotated Q/K vectors [head_dim] bf16

Interface

PortDirectionWidthDescription
vec_in [HEAD_DIM-1:0][15:0]in128×16Q or K vector for one head, one token position. 128 bf16 elements.
pos [15:0]in16Token position index (0..seq_len-1)
vec_out [HEAD_DIM-1:0][15:0]out128×16Rotated vector. Same shape as input.

Computation

// RoPE applies pair-wise 2D rotation to consecutive dimensions:
// For each pair (2i, 2i+1) where i ∈ [0..63]:
//   θ_i = rope_theta^(-2i/head_dim) = 500000^(-2i/128)
//   cos_pos = cos(pos × θ_i)    — precomputed, stored in ROM
//   sin_pos = sin(pos × θ_i)    — precomputed, stored in ROM
//
//   x_2i'   = x_2i × cos_pos - x_{2i+1} × sin_pos
//   x_2i+1' = x_2i × sin_pos + x_{2i+1} × cos_pos

Current implementation: vectorized host RoPE; no RoPE ROM is instantiated in the deployable PL path.
Stored in BRAM, indexed by position.

Latency: 1 cycle per pair (2 bf16 mults + 1 add/sub), 64 pairs → 64 cycles per token.
Can be pipelined: 4 pairs/cycle → 16 cycles per token.
RoPE Integration Point:
RoPE must be applied to Q and K after QKV projection and reshape to heads, but before the attention computation.
For the current implementation: RoPE is applied on the host side (ARM CPU) before writing Q and K to DDR. The FPGA attention accelerator receives pre-rotated Q and K.
Reason: RoPE is a lightweight element-wise operation (~2 MACs/element), and doing it on the host avoids adding a separate hardware module. If the host becomes a bottleneck, the rope_engine can be inserted between DDR load and the MAC array.

15.3 causal_mask.sv — Causal Attention Mask ext

Pipeline Position: Integrated into Scale step (between MAC Phase A and Softmax) 
// Causal mask: token at position i can only attend to positions j ≤ i
// mask[i][j] = 0 if j ≤ i, else -inf

// In the tiled FlashAttention loop:
// For Q_tile tokens at positions [q_start .. q_start+Tq-1]
// For K_tile tokens at positions [kv_start .. kv_start+Tk-1]
//
// If kv_start + j > q_start + i:
//     S[i][j] = -inf    (masked)
//
// This is a simple address comparator — no ROM needed.
// Integrated into the Scale step: S_scaled = S/√128 + mask
// Mask values: 0 (unmasked) or -65504 (≈ -inf in bf16)

15.4 rms_norm.sv — RMS Normalization ext

Pipeline Position: Before Attention (Pre-Norm in Llama3) ← Hidden states X [L, 4096] bf16 → Normalized X [L, 4096] bf16 
// RMSNorm(x) = x / sqrt(mean(x2) + ε) × γ
// where γ is a learnable scale parameter [4096] bf16
//
// Hardware implementation:
// Step 1: Square: x2 for each element (bf16 → fp32)
// Step 2: Reduce sum: Σ(x2) across 4096 elements → 1 fp32 value
// Step 3: Mean: sum/4096 + ε
// Step 4: Inverse sqrt: 1/√mean (LUT or Newton iteration)
// Step 5: Scale: x × inv_sqrt × γ → bf16

// This is a host-side operation in the current deployment.
// RMSNorm is applied before attention AND before FFN in Llama3's Pre-Norm architecture.

[Host] Read CSR_LOAD_REQ → configure DEST/LEN → call PYNQ DMA MM2S

╔══════════════════════════════════════════════════════════════════════════════╗
║                   PHASE 2: ATTENTION DOUBLE LOOP (16 Q_tiles × 8 KV_tiles)    ║
╚══════════════════════════════════════════════════════════════════════════════╝

[FSM] → ST_Q_INIT / ST_KV_READ / ST_QK_DOT / ST_SOFTMAX / ST_AV_DOT
[FSM]   group = 0..7, head = 0..3, q_tile = 0..15: // nested traversal

  // --- Q_tile Load ---
  [DDR:Q] → AXIS MM2S → [tile_buffer: Bank A]  32×128×2B = 8 KB, ~0.5 μs

  // --- Softmax State Init ---
  [softmax_engine] m/l state covers 16 hardware rows per microtile; two microtiles form TILE_Q=32
  [output_buffer] O_acc is updated for each 16×128 microtile

  [FSM]   kv_tile = 0..7:                        // inner loop

    // --- K/V Tile Read from URAM ---
    [kv_cache_ram] → K_tile[64][128] bf16  (read from URAM, ~10ns)
    [kv_cache_ram] → V_tile[64][128] bf16  (read from URAM, ~10ns)

    // --- Phase A: Q×K^T, 8 sub-blocks ---
    [tile_buffer] → Q[0..15][0..127] bf16
    [kv_cache_ram] → K[0..15][0..127] bf16
    [attn_tile] 16×16 MAC: Q×K^T → S_block[16][16] fp32  // ~128 cycles
    [attn_tile] → S_tile streams to softmax  // NOT stored in SRAM

    // --- Scale + Mask + Online Softmax ---
    [softmax_engine] S/√128 + causal_mask → S_scaled[16][16] fp32
    [softmax_engine] row_max = max(S_scaled, axis=1)  // log2(16)=4 cycle reduction
    [softmax_engine] m_new = max(m, row_max)
    [softmax_engine] correction = exp(m - m_new)       // 1 cycle EXP LUT
    [softmax_engine] P = exp(S_scaled - m_new)          // 1 cycle/element EXP LUT
    [softmax_engine] l = l*correction + sum(P)          // log2(16)=4 cycle reduction
    [softmax_engine] P_tile → streams to MAC Phase B

    // --- Phase B: P×V + Accumulate ---
    [attn_tile] P_tile[16][16] × V_tile[16][128] → ΔO[16][128] fp32
    [psum_accum] O_acc = O_acc × correction + ΔO
    [output_buffer] ← O_acc updated

  // --- After all KV tiles: normalize + writeback ---
  [softmax_engine] O = O_acc / l  →  O_tile[32][128] bf16
  [output_buffer] → AXIS S2MM → [DDR:O]  8 KB, ~0.5 μs

[FSM] → ST_DONE → interrupt host
